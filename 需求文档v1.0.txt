# 《智能赛事直播自动检测与 OBS 录制工具 V1.0》需求文档

## 1. 项目目标

开发一个 Windows 桌面 GUI 小工具，用于无人值守地监控多个固定直播网页。

以本次足球比赛为第一使用场景：

* 比赛预计北京时间 **02:00** 开始。
* 程序默认在 **01:55** 自动启动检测。
* 同时监控直播网站 A、网站 B。
* 哪个网站首先确认正在正常播放，就优先使用哪个网站。
* 自动尝试播放、切换最高画质、进入全屏。
* 确认视频真正开始播放后，通过 **OBS WebSocket** 自动开始录制。
* 录制过程中持续监控播放状态。
* 如果发生卡顿、网页异常或直播源失效，自动尝试恢复或切换备用网站。
* 比赛结束后自动停止 OBS 录制。
* 全过程必须写入详细日志，方便调试。

本版本重点不是追求复杂的 AI，而是建立一个**可靠的“检测 → 判断 → 播放 → 录制 → 监控 → 恢复”框架**，方便后续扩展。

# 5. 核心功能：直播状态检测

这是整个程序最重要的部分。

不能只判断网页是否打开。

必须尽可能判断：

> “这个网页上的视频是否真的已经开始正常播放。”

检测应该采用多种信号组合。

## 5.1 页面检测

检测：

* 网页是否正常加载
* 是否出现播放器
* 是否出现播放按钮
* 是否出现“直播中”等直播状态文字
* 是否出现“Live”等类似状态
* 是否出现等待/缓冲/错误提示

---

# 6. 播放器检测

如果网页使用 HTML5 Video：

优先通过浏览器脚本读取：

* video 元素是否存在
* `paused`
* `readyState`
* `currentTime`
* `duration`
* `videoWidth`
* `videoHeight`

重点：

连续检测 `currentTime` 是否发生变化。

例如：

第一次：

`currentTime = 125.20`

5 秒后：

`currentTime = 130.21`

说明视频正在播放。

如果连续多次：

`currentTime` 基本不变化，

则认为可能没有播放或者发生卡顿。

---

# 7. 点击播放

检测到播放器存在但尚未播放时：

自动寻找并点击播放按钮。

可能存在：

* Play
* 播放
* ▶
* 视频中央播放按钮
* 自定义播放器按钮

不能只写死一个 CSS 选择器。

应该设计成：

**多个候选选择器 + 失败后截图/日志记录。**

点击后必须再次检测视频是否真正开始播放。

不能：

> 点击按钮成功 = 播放成功

必须：

> 点击按钮 → 等待 → 检查 currentTime 是否持续变化 → 确认播放成功

---

# 8. 自动选择最高画质

播放成功后：

尝试寻找：

* 设置按钮
* 画质
* Quality
* 清晰度

然后选择当前可用的最高画质。

例如：

1080p

优先于：

720p

优先于：

480p

如果存在：

2160p / 4K

则优先选择 4K。

如果网站无法自动控制画质，则记录：

`无法自动设置画质`

不能因为画质设置失败而导致整个任务失败。

---

# 9. 自动全屏

播放成功后：

寻找全屏按钮。

尝试进入全屏。

如果浏览器或网站限制全屏：

记录日志，但不要停止任务。

---

# 10. 网站 A / 网站 B 的选择逻辑

这是非常重要的功能。

## 情况一：A 没有直播，B 有直播

直接使用 B。

## 情况二：A 有直播，B 没有直播

使用 A。

## 情况三：A、B 都没有直播

继续等待。

默认每：

**5 秒检测一次。**

每次检测都记录状态。

例如：

`01:55:05 A：未开播 B：未开播`

`01:55:10 A：未开播 B：未开播`

---

## 情况四：A、B 同时开播

默认优先使用 A。

但是不能仅仅因为 A 显示“直播中”就马上录制。

需要分别验证：

1. 页面正常
2. 播放器存在
3. 可以点击播放
4. 视频 currentTime 开始变化
5. 连续播放至少若干秒
6. 没有明显错误/缓冲状态

只有通过验证，才认为 A 是有效直播源。

如果 A 显示直播，但实际无法播放：

自动尝试 B。

---

# 11. “有效直播源”判断

建议建立一个简单评分机制。

例如：

| 检测项目             | 分数 |
| ---------------- | -: |
| 页面正常加载           | +1 |
| 找到播放器            | +2 |
| 检测到直播状态          | +2 |
| 成功点击播放           | +2 |
| currentTime 持续变化 | +3 |
| 播放器没有错误          | +2 |
| 视频分辨率正常          | +1 |

总分达到设定阈值，例如：

**7 分以上**

才认为直播源有效。

这样以后可以继续增加判断条件。

---

# 12. OBS 自动控制

使用 OBS WebSocket。

程序启动后先检查：

OBS 是否运行。

如果没有：

尝试启动 OBS。

然后连接 OBS WebSocket。

GUI 显示：

`OBS：已连接`

或者：

`OBS：未连接`

开始录制之前必须确认：

* OBS 已连接
* OBS 当前没有正在录制
* OBS 场景存在
* 录制目录可写

然后发送：

`StartRecord`

开始录制。

必须再次确认：

`OBS Recording = true`

才能认为录制真正开始。

---

# 13. 录制文件

文件名建议：

`日期_比赛名称_直播源`

例如：

`2026-08-20_Barcelona_vs_xxx_A.mp4`

具体文件格式和 OBS 编码参数由 OBS 自己控制。

程序只负责控制 OBS。

---

# 14. 录制过程监控

录制开始以后，程序不能什么都不管。

每隔例如：

**5～10 秒**

检查一次直播状态。

重点检查：

* currentTime 是否持续变化
* video 是否 paused
* 是否出现 buffering
* 页面是否崩溃
* 浏览器是否仍然存在
* 网络错误
* 播放器错误
* 是否仍然是直播状态

---

# 15. 卡顿判断

不要因为某一次检测 currentTime 没变化就马上判断卡顿。

采用连续检测。

例如：

检测间隔：

5 秒

如果：

第一次 currentTime = 500

第二次 = 505

第三次 = 510

正常。

如果：

第一次 = 500

第二次 = 500

第三次 = 500

第四次 = 500

则判断：

**疑似卡顿。**

可以设置：

`卡顿判定时间：20 秒`

即连续 20 秒没有有效播放进度变化，才正式判定卡顿。

---

# 16. 卡顿恢复机制

第一次发现卡顿：

等待 5 秒重新检测。

如果恢复：

继续录制。

如果仍然卡顿：

尝试：

1. 点击播放
2. 等待恢复
3. 如果失败，刷新页面
4. 等待页面重新加载
5. 再次尝试播放

如果网站 A 连续恢复失败：

切换到网站 B。

---

# 17. 切换直播源

如果当前 A 正在录制：

A 发生严重故障。

程序应该：

1. 判断 A 是否还能恢复
2. 尝试恢复
3. 如果超过设定时间仍无法恢复
4. 检测 B
5. 如果 B 有效
6. 切换到 B
7. 继续录制

注意：

**不能随意停止 OBS。**

V1.0 可以采用：

停止当前录制 → 切换网页 → 确认 B 正常 → 重新开始 OBS 录制。

后续版本再考虑无缝切换。

---

# 18. 结束条件

支持两种方式：

### 方式 A：最大录制时长

例如：

`150 分钟`

达到时间后：

停止 OBS。

### 方式 B：检测比赛结束

V1.0 不强制实现。

可以预留接口。

---

# 19. 异常保护

任何一个步骤失败，都不能直接让程序崩溃。

例如：

* Chrome 没启动
* 网页打不开
* 网站 A 失效
* 网站 B 失效
* 找不到播放按钮
* 找不到全屏按钮
* 找不到画质按钮
* OBS 没启动
* OBS WebSocket 连接失败
* 视频播放器改变了网页结构

都应该：

**记录错误 → 重试 → 必要时切换备用方案。**

# 25. 浏览器要求

优先使用 Playwright。

建议使用独立浏览器用户目录，避免影响用户正常 Chrome。

例如：

`browser_profile`

这样可以保存：

* 登录状态
* Cookie
* 网站设置
* 播放器偏好

如果网站要求登录，用户可以提前登录。

---

# 26. 网站兼容性设计

不要把代码全部写死在主程序里。

建议设计：

`SiteAdapter`

例如：

```text
SiteAdapter
 ├── detect_live()
 ├── find_player()
 ├── click_play()
 ├── set_max_quality()
 ├── fullscreen()
 ├── get_playback_time()
 ├── detect_error()
 └── recover()
```

网站 A 和网站 B 分别实现自己的 Adapter。

这样以后增加网站 C、D 时，不需要重写整个程序。

# 27. 第一版开发原则

第一版不要追求：

* AI 图像识别
* 自动理解所有网页
* 支持几十个网站
* 无缝切换
* 复杂云端服务

先把下面这条链路跑通：

**定时启动 → 打开 A/B → 检测直播 → 判断有效 → 播放 → 最高画质 → 全屏 → OBS 开始录制 → 监控 currentTime → 卡顿恢复 → 自动停止录制**

只要这条链路稳定，后面再增加智能判断。

# 29. 最重要的开发要求

**不要假设网页结构永远不变。**

所有关键操作都必须：

1. 尝试寻找目标元素
2. 操作
3. 等待
4. 验证结果
5. 失败后重试
6. 多次失败后记录日志
7. 必要时切换备用方案

例如：

不要写：

`点击播放按钮 → 认为播放成功`

必须写：

`点击播放 → 等待 → 检查 currentTime → 再检查一次 → 确认视频正在播放`

# 31. 给 Codex 的最终要求

请先按照本需求开发 **V0.1～V0.3**，不要一次性完成全部功能。

每完成一个阶段：

1. 保证程序可以启动
